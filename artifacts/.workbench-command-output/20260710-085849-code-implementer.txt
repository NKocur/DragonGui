# Spec: Default GUI Visual Polish And Density Audit

## Goal

Run a visual design audit similar to the existing `artifacts/visual_audit` workflow, but judge the default DragonGUI look and feel instead of only troubleshooting rendering defects. The output should identify and implement a first pass of default-theme and default-widget polish that makes GUI components, widgets, arrangements, and layouts look sleeker, more professional, and able to fit more useful data without requiring application authors to add custom CSS.

This is not a custom stylesheet showcase. Focus on the built-in defaults shipped by DragonGUI: default theme tokens, framework CSS, native primitive drawing, default control metrics, and default layout/chrome behavior.

## Visual Findings To Validate

Use screenshots and snapshots to confirm these design issues before making changes:

- Density: forms, property grids, sidebars, toolbars, and data-heavy panels use more vertical and horizontal space than needed for a professional workbench UI.
- Hierarchy: panels, cards, controls, tables, and plot frames often use similar borders and fills, so important interactive regions do not stand out clearly.
- Surface palette: the default dark palette leans heavily on nearby blue/purple surface colors. It is coherent but can read flat and monotonous across dense dashboards.
- Borders: many components rely on visible 1px borders. On clustered screens this creates visual noise and reduces perceived polish.
- Controls: buttons, small buttons, icon buttons, inputs, dropdowns, nav items, tabs, tree nodes, and selectable rows need more consistent default metrics and state contrast.
- Navigation: sidebars, nav rows, menu bars, and tabs should feel more like compact application chrome and less like standalone cards.
- Data surfaces: tables, property grids, log/code views, and plot containers should default to tighter rows, clearer headers, calmer gridlines, and less wasted padding.
- Mobile/narrow layouts: controls should remain readable and compact without text collisions, excessive empty space, or overly chunky chrome.

Do not treat every visual preference as a defect. Implement only changes that improve the default across many widgets and preserve existing behavior.

## Required Scope

Create a concrete default-look audit and polish pass covering at least these targets:

- Core controls: `Button`, `SmallButton`, `IconButton`, `ImageButton`, `ArrowButton`, `Dropdown`, `TextInput`, `TextArea`, `NumberInput`, `DragNumber`, `Checkbox`, `RadioButton`, `ToggleSwitch`, `Slider`, `RangeSlider`, `ProgressBar`.
- Navigation and workbench chrome: `Sidebar`, `NavItem`, `MenuBar`, `Menu`, `MenuItem`, `Tabs`, `Tab`, `Toolbar`, `Breadcrumbs`, `StatusBar`, `AppShell`, `WorkbenchLayout`.

- Layout containers: `Panel`, `Collapsible`, `ScrollArea`, `Splitter`, separators, nested panels, scrollable composites, plot embedding surfaces.

Deliver a first pass that should be visible in default probes without requiring app authors to set custom styles.

## Implementation Guidance

Start with analysis:

1. Inspect the current contact sheets and representative screenshots for `core-widgets`, `form-controls`, `tool-buttons`, `navigation-widgets`, `toolbar`, `tree-view`, `property-grid`, `data-table-upgrades`, `layout-scrollable-composites`, `layout-plot-embedding`, `app-shell-workbench`, and `responsive-layout`.
2. For each proposed polish change, identify whether the source is default theme/CSS/native metrics or probe-local CSS. Avoid changing product defaults to compensate for a probe-specific showcase style.
3. Record a concise before/after checklist in `artifacts/IMPLEMENTATION_NOTES.md`.

Default design direction:

- Keep the UI work-focused and compact. Prefer clearer information hierarchy and tighter metrics over decorative effects.
- Reduce repeated card heaviness: panels can remain framed, but nested panels and dense rows should avoid looking like stacks of thick boxes.
- Make controls slightly more compact by default while preserving touch/mouse usability and readable text.
- Use calmer surface separation: darker window background, slightly lifted panels, subtler borders, and stronger selected/focus states.
- Improve state contrast: hover, active, selected, disabled, and focus states should be obvious without overusing bright fills.
- Make data widgets denser by default: tighter rows, quieter gridlines, clear headers, and consistent numeric/text alignment where supported.
- Keep radii restrained. Do not make the default theme rounded or playful.
- Avoid a one-note purple/blue look. The built-in dark theme can keep an accent, but neutral surfaces should carry more of the interface.

Potential concrete changes to consider:

- Tune `Theme.dark()` and `Theme.light()` token values for more professional contrast and less saturated default surfaces.
- Reduce default `spacing` or selected component padding where it creates obvious waste, but do not globally shrink until text clipping is checked.
- Adjust `control_height()` and matching CSS heights only if button/input/text alignment remains correct.
- Differentiate `surface`, `surface_alt`, `border`, `muted_text`, `focus`, and disabled tokens enough that hierarchy is clearer.
- Add or adjust framework CSS for default part styling on `NavItem::item`, `NavItem::accent`, `Menu::item`, `ContextMenu::item`, scrollbar parts, table-like parts, toolbar separators, and tab/nav selected states if supported.
- Prefer subtle border opacity/color changes over adding large shadows. Use shadows only if already supported and visually restrained.

## Expected Behavior

After implementation:

- Default screens should show more data in the same viewport without feeling cramped.
- Dense widgets should have compact, legible rows and headers.
- Primary interactive controls should be visually identifiable but not oversized.
- Navigation and toolbar chrome should read as application structure, not as a collection of individual cards.
- Nested panels should maintain boundaries without excessive border noise.
- Focus and selected states should be clear for keyboard and mouse users.
- Disabled controls should still be recognizable and readable enough.
- Mobile/narrow captures should avoid overlap, clipped labels where avoidable, and unnecessarily large blank regions.
- Existing CSS override behavior should continue to work.

## Edge Cases

- Long labels in buttons, tabs, nav items, property names, table headers, and tree nodes.
- Very narrow mobile width around `390x720`, plus any existing `320x640` stress targets.
- High DPI / scale-factor rounding where 1px borders and text baselines can look uneven.
- Focus rings on small controls and icon-only buttons.
- Disabled, selected, active, hover, open, and checked states.
- Nested panels inside scroll areas, especially data-heavy dashboards.
- Tables with many columns and mixed numeric/text content.
- Scrollbar thumb visibility on dark surfaces.
- Existing app-level CSS that relies on default tokens or widget part names.
- Light theme parity if dark theme token names or metrics change.

## Out Of Scope

- Building a custom CSS theme for a single demo.
- Redesigning public widget APIs.
- Replacing the visual-audit harness.
- Large feature work such as new layout engines, new table virtualization, or new plotting behavior.
- Fixing unrelated rendering correctness bugs unless exposed directly by the default-polish work.
- Adding decorative hero/marketing styling, large gradients, or playful visuals to default workbench components.
- Removing application authors' ability to override defaults with CSS.
