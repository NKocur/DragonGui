# Spec: Reproduce And Fix Adjacent Plot Interaction Leakage

## Goal

The professional demo still exposes a plot-library bug. In the Explore page, a large left `Scatter3D` sits next to a smaller right `ScatterPlot2D` preview. The user reports that depending on where they click, data from the plot on the right can switch/combine with the neighboring plot. They reran the demo after the prior pass and still saw the same behavior.

A later pass fixed a separate startup-framing issue by making base `Scatter3D` startup uploads request `fit=True`. Keep that improvement, but do not treat it as the solution. The original click-dependent adjacent-plot interaction bug still needs a reproduction, a library fix, and verification in the package the user actually runs.

Also close the build/install gap. Bare global Python 3.13 currently imports the installed `site-packages` copy, not the workspace package. A source fix is not user-visible unless the demo run is proven to import the fixed workspace package or the global package is rebuilt/reinstalled.

## Required Outcomes

1. Reproduce the click-dependent bug.
   - Add a focused adjacent-plot probe/test with two distinct plot ids, point clouds, labels, and colors/colormaps.
   - Exercise clicks inside the left plot, inside the right plot, near the boundary/gutter, drag/release-outside, hover transitions, and wheel zoom where feasible.
   - Capture before/after debug snapshots and command history.

2. Fix adjacent plot state isolation at the library layer.
   - A click, drag, pick, hover, wheel, fit, or data update over one plot must not mutate the other plot unless the user explicitly linked cameras.
   - `SetScatterPointsPacked`, `FitScatterCamera`, hover metadata, scalar-bar state, actor operations, camera state, and selection state must target only the intended widget id.
   - `active_scatter_id`, `scatter_at(pos)`, pointer release, hover clearing, and wheel handling must not route later events to a stale neighbor.
   - `Scatter3D._camera_links` must remain explicit opt-in behavior.

3. Keep the startup-framing fix.
   - Base `Scatter3D` startup point data should still render in frame.
   - `ScatterPlot2D` should keep its 2D camera setup without duplicate or cross-target fits.

4. Improve audit/test coverage.
   - Static screenshot validation is not sufficient for this bug.
   - Add automated interaction coverage if the harness supports it, or add a focused command/debug reproduction script with documented expected invariants.
   - Visual audit should continue to fail nonempty scatter startup uploads that have neither `fit=true` nor a same-target `FitScatterCamera`.

5. Rebuild/reinstall or prove the run path.
   - Before marking complete, record both bare global Python and workspace import paths in `artifacts/TEST_RESULTS.md`.
   - If Python package code changes, reinstall into global Python 3.13 or run the demo with a verified workspace import path.
   - If native Rust code changes, rebuild the release extension and reinstall/copy the resulting `_dragongui.pyd`.
   - The final validated demo command must print or record `dragongui.__file__` and `dragongui._dragongui.__file__`.

## Implementation Guidance

Start with a minimal two-plot reproduction. Use explicit ids such as `left-scatter` and `right-scatter`, different data ranges, different colormaps, and different hover labels. The reproduction should be able to say, after each interaction, which scatter id was hit and which scatter ids changed.

Check these likely failure points:

- `scatter_at(pos)` using too-broad widget bounds instead of visible/clipped/scissored plot bounds.
- stale `active_scatter_id` after pointer up, release outside, or transition from one plot to another.
- wheel events over one plot using an earlier active scatter id.
- hover clearing or pick payload generation touching the wrong runtime.
- actor ids or primary payload caches reused across plot instances.
- camera-link propagation running for unlinked adjacent plots.

Fix the root cause in the library. A demo-only workaround is acceptable only as instrumentation or to make intended API behavior explicit.

## Expected Behavior

After the fix:

- The left and right Explore plots remain visually distinct after left, right, boundary, drag, hover, and wheel interactions.
- Clicking or dragging in the right preview plot cannot replace, combine, recolor, refit, or otherwise mutate the left plot's data.
- Clicking or dragging in the left plot cannot mutate the right preview plot's data.
- Debug snapshots keep distinct point counts, bounds, colormaps, camera states, actor counts, hover state, and selection state per scatter id.
- Startup framing remains fixed.
- The user's global Python 3.13 environment imports the fixed package, or the validated demo command explicitly imports the workspace package and extension.

## Edge Cases

- Two adjacent plots with no gap.
- Two adjacent plots separated by a splitter gutter.
- Nested plot inside a controls panel next to a larger plot.
- Clicks near pane boundaries and clipped plot corners.
- Pointer down in one plot and pointer up outside it.
- Wheel zoom over a plot inside a scrollable page.
- Hovering from one plot into another.
- `Scatter3D` plus `ScatterPlot2D`.
- Two `Scatter3D` widgets.
- Explicitly linked cameras should still propagate camera state.
- Unlinked cameras must never propagate.
- Empty data, one-point data, dense data, and categorical/scalar color data.
- Live `set_points`, `set_prepared_points`, actor add/update/remove, and clear operations.
- Re-rendering with stable keys and changed data.
- Global Python 3.13 importing a stale installed package or stale native extension.
- `pip install --force-reinstall .` producing a wheel but another path entry still shadowing it.
- Python-only changes where no native rebuild is needed but reinstall is still needed for `site-packages`.

## Out Of Scope

- Rewriting the professional demo layout.
- Removing the right preview plot to avoid the bug.
- Replacing the scatter renderer wholesale.
- Broad redesign of all chart widgets.
- Changing splitter sizing behavior unless it directly affects plot hit testing.
- Accepting a visual-audit `pass` while adjacent plot interactions mutate the wrong plot.
- Claiming the user-facing demo is fixed without proving the user-run Python imports the fixed package.
