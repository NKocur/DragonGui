The current artifacts still mark the professional demo route targets as `pass`, but several screenshots visibly fail professional layout expectations.

Concrete snapshot geometry:

This leaves roughly `545px` of the splitter unused. The table is squeezed to `360px`, so the screenshot shows mostly row indices rather than the actual route/owner/state data. The inspector controls are clipped in a `280px` pane even though the window has plenty of unused horizontal space.


This leaves about `307px` unused in the splitter. The `Scatter3D` plot area is constrained to the first pane minimum, while visual plot content appears cramped/clipped and the controls panel consumes an awkward narrow column.

```text
all-features-professional-overview-1180x760
Splitter: x=222 y=329 w=930 h=360
Pane 1/Fleet Pulse: x=222 y=329 w=320 h=360
Pane 2/Incident Mix: x=545 y=329 w=260 h=360
Recent Events panel: x=222 y=689 w=930 h=297
```

The overview chart/pie section uses only about `583px` of a `930px` splitter, leaving a large blank region to the right. The result looks unfinished and poorly organized.

Likely immediate root cause:

- `examples/all_features_professional_demo.py` uses `dg.Pane(size=0.62)`, `dg.Pane(size=0.38)`, `dg.Pane(size=0.72)`, `dg.Pane(size=0.28)`, `dg.Pane(size=0.7)`, and `dg.Pane(size=0.3)`.
- In the current Python API, numeric `Pane(size=...)` serializes as a fixed pixel size. A value like `0.7` means `0.7px`, not `70%`.
- In native layout, the tiny fixed size plus `min_size` makes panes clamp to their minimum widths and disables flex growth, so extra splitter space remains unused.
- This is an API/design footgun and a library/demo integration bug. The library should not silently produce professional-demo layouts where panes stick to minimum sizes and waste half of the available splitter.

## Required Outcomes

1. Fix splitter/pane sizing so splitters use available space.
   - Horizontal splitters with proportion-style pane intent must distribute available width after gutters.
   - Extra splitter space must not be left unused when panes have no max-size preventing growth.
   - The professional demo's overview/explore/data/reports splitters should fill their available width at `1180x760` and `1440x900`.

2. Make the Pane/Splitter API safer.
   - Decide and implement a clear behavior for fractional-looking `Pane(size=0 < n < 1)` and `Splitter(sizes=(0 < n < 1, ...))`.
   - Preferred options:
     - Treat `0 < size < 1` as a fraction/proportion of available splitter space, or
     - reject/warn on fractional numeric sizes and update the demo to use supported `fr` sizes or `flex`.
   - Do not continue silently treating `0.7` as a fixed `0.7px` pane in realistic app layouts.
   - Preserve support for explicit fixed pixel sizes such as `size=240`.
   - Preserve existing `'<number>fr'` sizes.

3. Fix the professional demo layout where needed.
   - Convert proportional pane usage to the corrected API.
   - Ensure `DataFrameTable` gets enough width to show meaningful columns on desktop.
   - Ensure `PropertyGrid`/inspector controls are not clipped in desktop/tablet captures.
   - Ensure plot panels use enough area to look professional and are not cramped into minimum-size panes.

4. Improve visual audit so these failures cannot pass.
   - Add snapshot validation for splitter utilization in `tools/visual_audit.py`, at least for `all-features-professional-*` targets.
   - A horizontal splitter should fail when child panes consume much less than the splitter width while there is no explicit max-size or intentional spacer explaining the unused area.
   - The validator should catch cases like `splitter.w=1190` with pane widths `360 + 280` plus gutter.

5. Verify the user's Python 3.13 path.
   - The user is running global Python 3.13. Confirm the same interpreter imports the local `python/dragongui/_dragongui.pyd` built from the current native code.
   - If the global Python is importing an installed/stale `dragongui` instead of the workspace package, document the exact import path and fix the run instructions/artifacts.

## Implementation Guidance

Start with the splitter failure. Do not chase chart/table rendering until the panes fill their container.

Suggested sequence:

1. Add regression tests for Splitter/Pane behavior.
   - Python serialization test:
     - `Pane(size=240)` remains fixed pixel size.
     - `Pane(size=0.7)` either serializes as a proportion/flex value or raises/warns according to the chosen API.
     - `Splitter(sizes=("7fr", "3fr"))` serializes expected flex values.
   - Native layout test:
     - Horizontal splitter width `1000`, gutter `6`, two panes with proportions `0.7/0.3` or `7fr/3fr`, min sizes `360/280`.
     - Assert panes plus gutter consume nearly the full splitter width.
     - Assert first pane is wider than its min size when space is available.
     - Assert max sizes still cap panes when supplied.

2. Fix the API/library behavior.
   - If choosing fractional support:
     - Interpret numeric `0 < size < 1` as proportional/flex, not fixed px.
     - Make native props unambiguous if needed, e.g. separate fixed `size` from flex/proportion.
   - If choosing rejection/warning:
     - Reject or warn for `0 < size < 1` as likely misuse.
     - Update the demo to use `Splitter(sizes=("7fr", "3fr"))`, `Splitter(sizes=("62fr", "38fr"))`, or `Pane(flex=...)`.
   - Ensure live `set_sizes(...)` follows the same semantics.

3. Update the professional demo.
   - Overview: Fleet Pulse and Incident Mix should fill the 930px splitter at `1180x760`.
   - Explore: Scatter pane and controls pane should fill the 930px splitter at `1180x760`.
   - Data: table and inspector should fill the 1190px splitter at `1440x900`.
   - Reports: HtmlReport and preview should fill available width.

4. Add visual audit validation.
   - For professional demo targets, parse snapshots and find nonzero horizontal splitters.
   - Sum direct child pane widths plus splitter gutter gaps.
   - If consumed width is much less than splitter width, fail with a note:
     - `Splitter underutilized: splitter width 1190, pane span 643`.
   - Avoid false positives for intentionally fixed splitters with explicit max sizes; if max-size detection is unavailable from snapshots, limit the validator to the known professional demo route splitters or use a conservative threshold.

5. Re-run visual audit and inspect screenshots manually.
   - The named screenshots should look materially different after the fix.
   - Do not approve if `data-1440x900` still shows only row indices or if `explore-1180x760` still leaves a large blank right side in the splitter.

## Edge Cases

- Numeric pane sizes below `1`.
- Fixed pixel pane sizes such as `240`.
- Existing `fr` splitter sizes.
- Live `Splitter.set_sizes(...)`.
- Pane `min_size` larger than proportional allocation.
- Pane `max_size` smaller than proportional allocation.
- Horizontal and vertical splitters.
- Nested splitters.
- Splitters inside scrollable pages.
- Splitters inside panels.
- DataFrameTable inside a resized pane.
- PropertyGrid editors inside a resized pane.
- Plot widgets inside resized panes.
- Global Python 3.13 importing stale installed package or stale native extension.

## Out Of Scope

- Rewriting the professional demo from scratch.
- Removing widgets or pages to avoid layout pressure.
- Dropping visual audit sizes.
- Replacing the entire layout engine.
- Broad table/chart renderer redesign before splitter geometry is fixed.
- Full interactive playback for menus/modals/drag/drop.
