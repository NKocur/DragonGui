# Spec: Isolate Adjacent Plot State And Fix Scatter Startup Framing

## Goal

The previous splitter/table pass improved pane sizing, but the professional demo still has a plot-library defect. On the Explore page, two plot widgets sit next to each other: a large primary `Scatter3D` on the left and a smaller `ScatterPlot2D` preview on the right. The user reports that depending on where they click, the data from the plot on the right can switch/combine with the neighboring plot. The saved visual audit also shows the large primary plot is still mostly blank/misframed even though it receives point data.

Fix this at the library layer, not by hiding or removing the demo's plots.

## Current Evidence

The current professional Explore page creates adjacent plots in `examples/all_features_professional_demo.py`:

- `state.scatter = dg.Scatter3D(...)` in the left pane.
- `state.scatter2d = dg.ScatterPlot2D(...)` in the right controls pane.

The refreshed audit log for `all-features-professional-explore-1180x760` shows both plots receive point data:

```text
target='dg-126' SetScatterPointsPacked ... colormap=turbo ... fit=false
target='dg-146' SetScatterPointsPacked ... colormap=viridis ... fit=false
target='dg-146' FitScatterCamera
```

There is no matching `FitScatterCamera` for `dg-126`, and the saved screenshots show the large primary `Scatter3D` is mostly blank/misframed while the smaller `ScatterPlot2D` preview renders points.

The interactive symptom adds a second required check: adjacent plot interactions must stay instance-local. A click, drag, pick, fit, hover, or data update over one plot must not apply camera state, selection state, hover metadata, point buffers, actors, or colormap state to the other plot unless the user explicitly links cameras.

## Required Outcomes

1. Initial `Scatter3D` data renders in-frame.
   - A `Scatter3D` with startup point data must issue or otherwise apply a camera fit before/with first render unless the API explicitly opts out.
   - `ScatterPlot2D` can keep its existing 2D camera sync, but it must not be the only scatter-like widget that frames initial data.
   - The primary Explore plot must show its point cloud in `all-features-professional-explore-1180x760.png` and `all-features-professional-explore-1440x900.png`.

2. Adjacent plot state is isolated by widget id.
   - `SetScatterPointsPacked`, `FitScatterCamera`, hover metadata, scalar-bar state, actor operations, and camera/picking operations must target only the intended widget id.
   - `active_scatter_id`, `scatter_at(pos)`, pointer capture/release, hover clearing, and wheel handling must not leave stale state that lets an interaction in the right plot mutate the left plot or vice versa.
   - `Scatter3D._camera_links` must only propagate camera state between explicitly linked widgets, never between adjacent plots by default.
   - Re-render/diff paths must not reuse cached payloads or widget ids in a way that causes one plot's data to appear in another plot.

3. Reproduce and guard the click-dependent bug.
   - Add a focused probe or test scenario with two adjacent plots using different data, colors, and labels.
   - Simulate clicks/drags/wheel over each plot and verify debug snapshots/command history keep operations scoped to the hit plot's id.
   - Verify the right plot's data cannot combine with the left plot's data after clicking near boundaries, inside the gutter, inside the right plot, or inside the left plot.

4. Improve visual audit coverage.
   - The audit must fail when a plot with uploaded point data renders as an effectively blank/misframed plot.
   - The audit should include a two-adjacent-plots interaction check, either in the professional Explore route or a smaller probe.
   - Static screenshots alone are not enough for this bug; add automated interaction steps if the audit harness supports them, or document the manual reproduction command and expected debug invariants.

## Implementation Guidance

Start with a small reproduction instead of only the full professional demo.

1. Build a probe/test with two adjacent scatter widgets:
   - left: `Scatter3D` with one data cloud and a distinctive colormap/axis labels.
   - right: `ScatterPlot2D` or another `Scatter3D` with different data and a different colormap/axis labels.
   - Give both explicit ids so logs/snapshots are easy to assert.

2. Verify startup command targeting:
   - Both widgets should receive their own point upload.
   - The primary `Scatter3D` should also receive a fit or have equivalent native initial-camera logic.
   - A fit command for the right plot must not change the left plot unless cameras are explicitly linked.

3. Verify runtime interaction targeting:
   - Click/drag/wheel inside the left plot: only left camera/selection/hover state changes.
   - Click/drag/wheel inside the right plot: only right camera/selection/hover state changes.
   - Click near the boundary/gutter: either no scatter target or the geometrically containing topmost plot; never both.
   - Pointer release should clear stale `active_scatter_id` when no scatter interaction remains active.

4. Fix root cause:
   - If the issue is missing startup fit, make `Scatter3D` fit its initial payload by default or add an explicit constructor option and update the demo to use it.
   - If the issue is stale `active_scatter_id`, tighten pointer lifecycle and clear stale ids when the cursor leaves/releases outside the active plot.
   - If the issue is hit testing, use visible/clipped plot rects rather than broad widget bounds.
   - If the issue is payload/cache reuse, key caches by widget id plus payload token and ensure actor ids are per-scatter, not globally applied to the wrong runtime.

## Expected Behavior

After the fix:

- `all-features-professional-explore-1180x760.png` and `all-features-professional-explore-1440x900.png` show visible point content in the large left `Scatter3D`.
- Clicking or dragging inside the right preview plot does not change, combine, replace, or recolor the left plot's data.
- Clicking or dragging inside the left plot does not change, combine, replace, or recolor the right preview plot's data.
- Fit/reset actions target the intended plot or all intended plots explicitly; there is no implicit neighbor coupling.
- Debug command history clearly records target ids for scatter point uploads, fits, camera changes, picks, and selections.

## Edge Cases

- Two adjacent plots with no gap.
- Two adjacent plots separated by a splitter gutter.
- Nested plot inside a controls panel next to a larger plot.
- Clicks near pane boundaries and clipped plot corners.
- Pointer down in one plot and pointer up outside it.
- Wheel zoom over a plot inside a scrollable page.
- Hovering from one plot into another.
- `Scatter3D` plus `ScatterPlot2D`.
- Two `Scatter3D` widgets.
- Explicitly linked cameras should still propagate camera state.
- Unlinked cameras must never propagate.
- Empty data, one-point data, dense data, and categorical/scalar color data.
- Live `set_points`, `set_prepared_points`, actor add/update/remove, and clear operations.
- Re-rendering with stable keys and changed data.
- Global Python 3.13 importing a stale installed package instead of the workspace package.

## Out Of Scope

- Rewriting the professional demo layout.
- Removing the right preview plot to avoid the bug.
- Replacing the scatter renderer wholesale.
- Broad redesign of all chart widgets.
- Changing splitter sizing behavior from the prior pass unless it directly affects plot hit testing.
- Accepting a visual-audit `pass` while the primary plot is blank or adjacent plot interactions mutate the wrong plot.
