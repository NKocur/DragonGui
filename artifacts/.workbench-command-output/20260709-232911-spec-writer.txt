## Failure Inventory

### 1. `app-shell-workbench`

Symptoms:

- Desktop and `390x720` screenshots show the sidebar, but the `WorkbenchLayout` / `Body` / `WorkbenchMain` content area is blank except for a scrollbar.
- `StatusBar` is not visible in the viewport.
- Snapshot shows right-side body content laid out thousands of pixels below the viewport.
- Many body descendants have `w: 0.0`; examples from desktop snapshot:
  - first body label `dg-12`: `x: 190`, `y: 0`, `w: 0`, `h: 725`
  - second body label `dg-13`: `x: 190`, `y: 739`, `w: 0`, `h: 1756`
  - `WorkbenchMain` scroll area `dg-24`: `x: 190`, `y: 3581`, `w: 20`, `h: 0`
  - `StatusBar` `dg-43`: `x: 190`, `y: 3581`, `w: 850`, `h: 34`

Likely area:

- `native/src/layout.rs`
- Python layout defaults in `python/dragongui/widgets.py` for `AppShell`, `WorkbenchLayout`, `Body`, and `WorkbenchMain` only if the native behavior is correct but defaults are wrong.

The bug class appears to be row/flex child sizing and scroll-owner height resolution for an `AppShell` horizontal root containing a fixed `Sidebar` and a vertical `WorkbenchLayout` with `Body` plus `StatusBar`. `Body` currently supplies `width: 0` when no explicit width is passed; verify whether that is intended as flex-basis behavior or is collapsing descendants in the native/Taffy lowering.

Expected behavior:

- `Sidebar` keeps its fixed width.
- `WorkbenchLayout` fills the remaining width and visible height.
- `Body` is visible above `StatusBar`, owns vertical scrolling, and its children have nonzero content width.
- `WorkbenchMain` appears inside the body at its fixed height.
- `StatusBar` is pinned below the body inside the workbench area and remains visible at desktop and `390x720`.

### 2. `form-controls` at `390x720`

Symptoms:

- Mobile screenshot shows the Theme stress test button row clipped/overlapped by the following Text entry panel.
- Desktop capture is acceptable.
- Snapshot shows the `Theme stress test` panel at `h: 118` while its button row appears too low for the panel body (`dg-8` y-position extends below panel bottom).
- Later `GridLayout` children also show widths wider than their containing grid at `390x720`:
  - `grid_layout` `dg-33`: `w: 330`
  - child panels `dg-34` / `dg-43`: `w: 390`

Likely area:

- `native/src/layout.rs`
- Possibly probe CSS only if the probe has impossible desktop-only min constraints, but prefer fixing native layout if the same bug class appears in other targets.

Expected behavior:

- Titled panels reserve enough title/body height for their children at narrow widths.
- Responsive `GridLayout` children should not exceed the grid content width at `390x720`.
- The theme button row should be fully visible, and the following text-entry panel should start after the theme panel.

### 3. `layout-flex-stress` at `390x720`

Symptoms:

- Dense rows are squeezed/truncated and lose usable width.
- Several flexible controls are laid out with `w: 0.0`, including:
  - text input in the first stress row
  - range slider in nested row
  - buttons in action row
  - small buttons in constrained card row
- Fixed labels of `172px` plus gaps and fixed action buttons can exceed available row width; the current engine allocates zero width to flexible children instead of wrapping/reflowing or preserving a minimum usable width.

Likely area:

- `native/src/layout.rs`
- Potentially `examples/css_feature_probes/layout_flex_stress_probe.py` only to express intended wrapping with `FlowLayout` where an `HLayout` cannot reasonably fit. Do not hide a real native flex-shrink bug by only loosening the probe.

Expected behavior:

- Flexible controls with `flex: 1`, `flex-shrink: 1`, `min-width: 0` should stay within row bounds without becoming unusably zero-width when there is available remaining width.
- Where a row cannot physically fit all fixed elements, the target/probe should use `FlowLayout` or native layout should preserve a usable control width and avoid text/control overlap.
- No child should paint outside its panel's right edge in the `390x720` capture.

### 4. `responsive-layout` at `390x720`

Symptoms:

- Content clips off the left edge and overlaps vertically.
- `Auto sizing` panel has `x: -37`, `w: 440` inside a narrow viewport because CSS has `min-width: 440` plus auto side margins.
- `Auto-fit and dense placement` and `fit-content and minmax tracks` overlap vertically:
  - auto-fit grid starts at `y: 801`, `h: 220`
  - following fit-row panel starts at `y: 1033`, but descendants from auto-fit extend below this region.
- Existing full native test artifacts already reported layout failures involving percent/calc sizing and flow auto-width behavior; those are relevant here.

Likely area:

- `native/src/layout.rs`, especially:
  - percent/calc lowering and parent-size resolution
  - auto margins with min/max widths
  - CSS grid auto-fit/auto-fill/dense placement height reconciliation
  - post-layout reflow of column siblings after grid packing
- `examples/css_feature_probes/responsive_layout_probe.py` only if a probe rule intentionally sets a minimum width larger than mobile and should instead demonstrate responsive collapse.

Expected behavior:

- Narrow viewport content should stay within the visible horizontal bounds or intentionally scroll horizontally if configured. This probe is not a horizontal-overflow stress case.
- Auto-width/min-width panels should not be centered to negative x in a scroll-root that is intended to fit the viewport.
- Grid auto-placement height must include all packed children before following siblings are positioned.
