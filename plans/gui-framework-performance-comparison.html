Where DragonGUI stands against efficient Python GUI frameworks

DragonGUI is already competitive in steady GPU rendering and batched updates—generally second to Dear PyGui—but native startup and process memory are now the dominant gaps.

How to read this responsibly

Build time is not time-to-interactive
DragonGUI's public build creates its Python retained tree, then defers native document parsing, cascade, layout, text preparation, GPU setup, and presentation to blocking App.run(). Qt and Dear PyGui create more native state during their build/setup stages.
DragonGUI first-present latency is not yet exposed
The report intentionally leaves DragonGUI's “first event” blank. Its fresh lifecycle shows roughly three seconds of excess native initialization, but the runtime needs monotonic stage timestamps before that can be broken down fairly.
Process RSS is a warning signal, not a heap attribution
RSS includes native libraries, allocator retention, driver mappings, shared GPU memory, atlases, buffers, and pipeline caches. Dense DragonGUI results were bimodal. Adapter identity and CPU/GPU byte accounting are required before assigning a per-widget cost.
This is a controls benchmark, not a universal framework ranking
It does not yet compare scatter plots, large virtualized tables, accessibility, complex text editing, resize latency, platform integration, or application architecture. Qt's mature invalidation and model/view systems may behave very differently in other workloads.

Recommended next priorities

P0

Instrument and reduce startup

  1. Timestamp adapter/device creation, document parse, cascade, layout, pipelines, submit, and first present.
  2. Expose adapter, backend, driver, device type, and limits.
  3. Lazily create shaders and pipelines absent from the initial document.
  4. Add a first-present exit mode for direct startup comparisons.
P0

Attribute memory precisely

  1. Report retained tree, styles, provenance, layout, text, and CPU buffer bytes.
  2. Report GPU buffers, textures, atlases, pipelines, and cache bytes separately.
  3. Investigate the 207–484 MiB dense-run split before optimizing by assumption.
P1

Measure mutation-to-present

  1. Carry one update ID from Python mutation through queue, rebuild, submit, and presentation.
  2. Benchmark 1, 10, 100, and 1,000 mutations per frame.
  3. Use end-to-end p50/p95/p99 instead of adding separately sampled phases.
P2

Benchmark DragonGUI's differentiators

  1. 100k, 500k, and 1M point scatter upload, replacement, and steady rendering.
  2. 100k and 1M row virtualized tables with 20 columns.
  3. Streaming plots, background-thread updates, resize, and deep-layout scrolling.
