Interpretation

DragonGUI’s GPU stage is not the main bottleneck.At high load, native frame work p95 was 0.60 ms while command drain p95 was 36.88 ms. The dominant cost is applying Python-originated changes and rebuilding affected retained content.
Coalescing makes overload bounded and correct.The recommended high-load run coalesced 2,080 obsolete tasks, held Python queue high-water to 1, drained fully, and finished on the correct final tick.
DragonGUI keeps substantially less high-load memory than Dear PyGui.Peak RSS was 251 MiB versus 788 MiB, although PyQtGraph remained lowest at 124 MiB.
Batch transport and targeted invalidation moved the practical ceiling.DragonGUI sustains 60.0 Hz at medium load with frame-work p95 of 0.71 ms. At high load, Python submission and command application—not GPU frame work—remain the limiting path.

Method and fairness notes

Each framework displays the same deterministic data shapes and control counts. Low uses two 2k-point lines; medium uses four 10k-point lines; high uses six 50k-point lines plus a 50k-point scatter, a 128×128 heatmap, and 200 changing labels. Frameworks run in fresh processes. Synchronous event-loop adapters skip overdue scheduled generations; DragonGUI’s producer uses keyed latest-frame coalescing and submits each generation through the batch property-update path, which gives equivalent latest-state semantics with bounded queues.

Validation checks retained point counts, heatmap dimensions, final visible status, scheduled-tick accounting, and item existence. DragonGUI additionally checks native resources, renderer source counts, native retained text, layout diagnostics, and drained queues. All 99 checks passed. One repetition makes this an engineering baseline rather than a statistically conclusive ranking.
