Engineering conclusions

Fixed-width live labels still trigger measurement churn.At 320 labels, 96,350 distinct measurements and 5 capacity clears drive native apply p95 to 20.15 ms. These labels are explicitly fixed-width and non-wrapping, so layout should be able to avoid most of this work.
LED updates double the property fan-out.Calling set_on() for 320 LEDs creates 641 properties per frame because both state and color are submitted. Deduplicating unchanged states and combining LED state/color application are high-confidence targets.
Progress paint is not free, but it is not the first target.At 320 channels, progress-only application p95 is 12.18 ms and CPU is 33.8%. It matters after label invalidation and LED fan-out are fixed.
The GPU renderer is not the limiter.Combined stage frame-work p95 is only 0.88 ms. The overload occurs earlier in property application, text/layout invalidation, and command draining.

Recommended optimization order

  1. Add a fixed-geometry text update path: changing non-wrapping text inside an explicitly sized label should rebuild glyph content without invalidating layout or populating the layout-measure cache.
  2. Make LED.set_state()/set_on() a no-op when the effective state and color do not change; send one composite update when they do.
  3. Profile native property-packet application by property family, then reduce repeated lookup/dirty propagation across hundreds of sibling targets.
  4. Re-run this exact matrix, then the full three-framework telemetry report, after each optimization.
