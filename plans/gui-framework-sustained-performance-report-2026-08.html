XY applicability

Scatter only; not folded into the framework charts

XY is a browser/WebGL plotting library, not a general desktop-widget toolkit, so it has no comparable control, mutation, CSS, resize, or table cases here. Its separately executed 1M-point wheel benchmark recorded a 20.4 ms post-gesture settle and 4.10/5.30 ms p50/p95 gesture samples in XY’s trusted-CDP/SwiftShader harness. DragonGUI’s native OS-input run first reached the correct image in 121.68 ms and reached frame-generation stability in 340.16 ms. These are useful directional diagnostics, not a ranked latency chart: the event source, rendering stack, and completion probes differ.

DragonGUI internals

What the native pipeline says

Demonstrated strengths

  • Public construction at 2,502 widgets is 13.77 ms, ahead of Dear PyGui (27.18 ms) and PyQt6 (132.35 ms).
  • 100k packed-line submission is 3.81 ms, ahead of Dear PyGui (6.45 ms) and the Qt painter (91.75 ms).
  • Completed 400-mutation active-frame p95 is 0.57 ms, below Dear PyGui (1.44 ms), PyQt6 (23.65 ms), and Tkinter (150.70 ms).
  • The virtualized table handles 100k rows without active-frame growth proportional to row count.

Optimization priorities

  • Reduce native retained memory per widget; dense controls use 346 MiB at 500 rows versus Dear PyGui’s 62 MiB.
  • Incrementalize first/full cascade work and investigate style reapplication at large widget counts.
  • Investigate platform resize dispatch and long operation-window lifetime separately from frame work.
  • Keep input-to-photon latency and cross-stack plotting comparisons in dedicated, matched harnesses.

Still outside this report

  • GPU/CPU utilization and energy consumption.
  • Input-to-photon latency, scrolling, text editing, and accessibility.
  • Images, heatmaps/scatter, multi-window work, terminal throughput, and long-duration memory stability.
  • Cross-machine, Linux/macOS, integrated-GPU, and release-wheel validation.
Method and interpretation

Fair enough to guide work, not a universal leaderboard

Every sample ran in a fresh process; framework order rotated by case and repetition. Dynamic cases used 30 operations (tables used 10), paced toward 60 Hz, with three repetitions. DragonGUI operations begin after application_frame_presented. Its queued Python submission, native command drain, style/layout telemetry, and frame-work sampler are reported separately. The DragonGUI mutation runner is deliberately held open until its planned update stream finishes; this fixes the prior lifecycle mismatch with its uncapped native frame loop.

Qt line rendering uses a small public QWidget/QPainter.drawPolyline implementation rather than a third-party plotting package. Qt tables use QAbstractTableModel/QTableView. These are appropriate public primitives, but the plot result is not a claim about every Qt plotting library. Dear PyGui uses its native line series. Tk participates only in the common control cases.

Architecture references: Dear PyGui’s retained/GPU model, Qt model/view, QAbstractTableModel, and QPainter polyline APIs.
