# V3 HTML Report Viewer

DragonGUI should support viewing trusted HTML reports generated by tools such
as Plotly, pandas profiling/report generators, notebook exporters, and internal
analysis pipelines. These reports are not just styled text: Plotly output
usually requires JavaScript execution, DOM layout, CSS, SVG/canvas/WebGL, and
interactive pointer events. The right implementation target is therefore an
embedded browser-backed report widget, not a native HTML subset renderer.

The first version should be Windows-first using WebView2, with a reliable
external-browser fallback on unsupported platforms or when WebView2 is not
available.

## Goals

- Add an `HtmlReport` or `HtmlView` widget for local trusted HTML reports.
- Support Plotly single-file and asset-folder reports.
- Preserve report interactivity: hover, pan, zoom, modebar, legends, and links.
- Track the widget's layout rect so the browser view resizes with DragonGUI.
- Provide a clear fallback that opens the report in the system browser.
- Keep report loading isolated from the normal WGPU primitive/text render path.
- Make the security model explicit: trusted local reports by default.
- Add a focused probe with a generated Plotly report when Plotly is installed,
  plus a minimal self-contained HTML fallback report for CI/smoke tests.

## Non-Goals

- Implementing a native HTML/CSS/JS engine.
- Full web browser navigation as a general app surface.
- Arbitrary untrusted internet browsing inside DragonGUI.
- Cross-platform embedded webview support in the first milestone.
- Compositing browser pixels into WGPU textures in the first milestone.
- Supporting WebView content inside transformed/clipped/rotated containers.
- Supporting multiple overlapping embedded browser widgets as a first-class
  production scenario in the first pass.

## Proposed Python API

Basic local report:

```python
report = dg.HtmlReport("reports/run_42.html", height=520)
```

Named widget with explicit local policy:

```python
report = dg.HtmlReport(
    "reports/plotly_dashboard.html",
    id="run-report",
    allow_remote=False,
    allow_scripts=True,
)
```

HTML string for generated reports:

```python
html = fig.to_html(include_plotlyjs="cdn", full_html=True)
report = dg.HtmlReport.from_html(html, base_dir="reports")
```

Open externally fallback:

```python
report.open_external()
```

Live replacement:

```python
report.set_path("reports/latest.html")
report.set_html(fig.to_html(full_html=True), base_dir="reports")
report.reload()
```

Suggested constructor:

```python
class HtmlReport(Widget):
    def __init__(
        self,
        path: str | Path | None = None,
        *,
        html: str | None = None,
        base_dir: str | Path | None = None,
        allow_remote: bool = False,
        allow_scripts: bool = True,
        external_fallback: bool = True,
        width: float | None = None,
        height: float | None = 480,
        id: str | None = None,
        class_: str | None = None,
        style: Mapping[str, Any] | None = None,
        parent: Container | None = _DEFAULT_PARENT,
    )
```

## Widget Properties

Native props should remain small:

- `html_report_path`: local file path to load.
- `html_report_html_resource`: optional resource id for string-backed HTML.
- `html_report_base_dir`: base directory for relative assets.
- `html_report_allow_remote`: whether remote navigation/resource loading is allowed.
- `html_report_allow_scripts`: whether script execution is allowed.
- `html_report_external_fallback`: whether to open externally if embedded load fails.
- `html_report_status`: load state for debug snapshots.

Python should validate:

- exactly one of `path` or `html` is provided
- paths are non-empty and point to files when possible
- `base_dir` is required for relative assets when using raw HTML strings
- unsafe remote URLs are rejected unless `allow_remote=True`

## Architecture

### Recommended First Implementation

Use a platform browser child/overlay window for the embedded view.

On Windows:

- Use WebView2 as a child of the main DragonGUI window.
- Create/destroy a native WebView instance for visible `HtmlReport` widgets.
- Position it from the computed widget `Rect` each frame or when layout changes.
- Hide it when the widget is not visible, its page is inactive, or a modal should
  occlude it.
- Route focus into WebView when clicked and back to DragonGUI when focus leaves.
- Load local files via file URLs or temporary generated files for string HTML.

On non-Windows:

- Render a native placeholder panel with status text and an "Open" button.
- `open_external()` uses the system browser.
- Leave Linux/macOS embedded backends as later milestones.

### Why Not Native HTML Rendering

Native rendering would work only for simple static documentation. Plotly reports
need JavaScript, SVG/canvas/WebGL, hover events, zoom handling, and modebar
controls. Reimplementing enough of a browser to make Plotly work is not a
practical DragonGUI widget project.

### Why Not Offscreen Browser Texture First

An offscreen CEF/WebView-to-WGPU texture path would integrate better visually,
but it is substantially harder:

- browser lifecycle and GPU context coordination
- pixel buffer upload or shared texture interop
- IME/focus/text input routing
- pointer coordinate transforms
- high-DPI scaling
- scroll/clip/modal composition
- larger binary/package footprint

The child-window WebView2 approach gives useful Plotly report viewing sooner.

## Native Runtime Work

Add `WidgetKind::HtmlReport`.

Document parsing:

- parse the new props in `document.rs`
- include props in runtime debug snapshots
- add `html_report` to CSS/widget catalogs

Layout:

- default intrinsic size around `640x480`
- honor explicit width/height/min/max/flex sizing
- no native children in the first pass

Primitives/text:

- draw a placeholder background/status when embedded view is unavailable
- draw a loading/error frame if WebView creation fails
- avoid painting over active WebView content unless the WebView is hidden

Runtime:

- track a map of `html_report_id -> platform view`
- create platform views after the main window is available
- update view bounds after layout
- hide/destroy views when widgets disappear
- reload on path/html/security-prop changes
- include per-view diagnostics in debug snapshots

Commands:

- `SetHtmlReportPath`
- `SetHtmlReportHtml`
- `ReloadHtmlReport`
- `OpenHtmlReportExternal`

Events:

- click/focus handoff to WebView
- optional `on_load`, `on_error`, and `on_navigation` callbacks later

## WebView2 Policy

Default policy should be strict because reports may contain arbitrary HTML:

- local files only by default
- no remote top-level navigation unless `allow_remote=True`
- consider blocking `file://` traversal outside `base_dir` for string-backed reports
- allow scripts by default because Plotly needs JavaScript
- expose no native bridge/API to the page in the first implementation
- open external links in the system browser unless explicitly allowed in-widget

## Python API Work

- Add `HtmlReport` to `python/dragongui/widgets.py`.
- Export it from `python/dragongui/__init__.py`.
- Add live methods:
  - `set_path(path)`
  - `set_html(html, base_dir=None)`
  - `reload()`
  - `open_external()`
- Add validation tests in `tests/test_python_api.py`.
- Add VDOM serialization tests in `tests/test_vdom.py` if needed.

## Probe

Add `examples/css_feature_probes/html_report_probe.py`.

The probe should:

- generate a small self-contained local HTML report with inline JavaScript
- optionally generate a Plotly report if Plotly is installed
- show one embedded `HtmlReport`
- include controls:
  - reload
  - swap report
  - open external
  - toggle embedded/fallback mode if supported
- show status labels for load state and platform support

The fallback HTML should not require network access.

Example fallback report content:

- header and summary stats
- simple SVG chart
- a small JavaScript interaction, such as toggling a trace or updating text

## V3 Demo Integration

Add a "Reports" or "Debug / Reports" section to `examples/all_features_v3_demo.py`.

The section should show:

- one static report viewer card
- one button to open the same report externally
- explanatory status only when embedded support is unavailable

Avoid making the report viewer part of the initial overview if WebView startup is
expensive. It should be lazily created when the section becomes visible if the
platform layer supports lazy creation.

## Milestones

### Milestone 1: API And Fallback

- Add `HtmlReport` Python widget and serialization.
- Add native `WidgetKind::HtmlReport`.
- Render native placeholder/status.
- Implement `open_external()` command.
- Add tests and a probe that works without embedded WebView.

### Milestone 2: Windows WebView2 Prototype

- Create a WebView2 child view for one visible report widget.
- Load local file paths.
- Update bounds on layout changes and window resize.
- Hide on page switch and when not visible.
- Add debug snapshot state.

### Milestone 3: Robust Report Loading

- Support raw HTML string resources via temporary files or resource-backed URLs.
- Support `base_dir` for relative assets.
- Add reload and path/html live updates.
- Add navigation policy for external links and remote URLs.

### Milestone 4: Interaction Polish

- Focus handoff and keyboard behavior.
- Scroll behavior when embedded inside scroll areas.
- Modal/page/sidebar occlusion rules.
- Multiple report instances, with explicit limits if needed.

### Milestone 5: Demo And Documentation

- Add the V3 demo section.
- Add docs examples for Plotly reports.
- Document Windows-first embedded support and fallback behavior.
- Document security defaults.

## Open Questions

- Should the widget be named `HtmlReport`, `HtmlView`, or `WebView`?
- Should remote CDN Plotly resources be blocked by default, or should local
  trusted reports be allowed to reference CDN scripts with an explicit flag?
- Should WebView2 be an optional feature in `native/Cargo.toml`?
- Should embedded views be limited to one active instance initially?
- How should WebView content interact with DragonGUI modals and overlays?
- Should raw HTML strings be stored in the resource registry or written to a
  temporary file before loading?

## Risks

- Native child-window z-order may not compose with WGPU overlays.
- Scroll areas and clipping may be awkward with platform child windows.
- WebView2 runtime availability varies across Windows installations.
- Bundling/packaging WebView2 support can complicate releases.
- Security policy needs to be conservative and easy to understand.
- Cross-platform support will require separate backend decisions.

## Recommendation

Start with `HtmlReport` as a Windows-first embedded WebView2 widget plus
external-browser fallback. Keep the scope explicitly focused on trusted local
analysis reports, especially Plotly output. Do not attempt native Plotly/HTML
rendering, and do not start with offscreen browser texture composition unless
child-window WebView2 proves unusable for the intended reports.
