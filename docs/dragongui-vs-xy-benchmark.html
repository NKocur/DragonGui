What XY demonstrates

  • Separate exact source columns from disposable render buffers.
  • Switch dense overviews to a screen-bounded density grid.
  • Keep adaptive payloads near 256 KiB from 1M through 5M rows.
  • Stop benchmarks only after pixels are correct and stable.

What DragonGUI already does well

  • Retained-frame averages stay under 6.3 ms through 4M points.
  • Exact rendering scales without XY's browser-process footprint.
  • Packed NumPy ingestion and native upload are not the cold-start bottleneck.
  • A native desktop runtime remains attractive for sustained tools.

Immediate engineering priorities

  • Guard every GPU allocation and eliminate native capacity panics.
  • Replace the 64-byte point expansion with compact attribute buffers.
  • Apply reduction before allocation and add density aggregation.
  • Instrument the roughly 5.2-second startup queue gap.
Method

Same rows, different presentation stacks

Both libraries receive seeded correlated Gaussian float32 x/y arrays with five planted sentinels. Package import and data generation are excluded. XY total time combines production Python figure/payload construction with browser navigation to a correct image and ten byte-identical frames. DragonGUI time covers public widget construction plus App.run() through 20 native frames after confirming the source count, native update, and application presentation.

Adaptive modes target the same user outcome but are not algorithmically identical: XY uses density above 200k rows while DragonGUI uses stride LOD factor 8. The exact table is the stricter engine-to-engine comparison.

Interpretation limits

Directional, not universal

  • One Windows machine and three samples per successful cell.
  • XY's headless Chrome used SwiftShader; DragonGUI used its native wgpu adapter. This biases browser timing against XY.
  • XY performs pixel readback validation; DragonGUI validates native state and completed frames.
  • Memory pools cannot be collapsed without hiding Chrome's process baseline.
